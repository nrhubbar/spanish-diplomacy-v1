Thirteen public actions and one internal. Each is POST /<Action> with a JSON body, so the list above is the whole surface.

Games with only computers

StartGame on a Game whose Seats are all computers makes the Turn Lambda play it to its end, or to a turn limit. You read it with ListTurns, as you suggested. Nobody is waiting, so its Turns are shown unfiltered to the host. The balance harness stays on your machine, where thousands of games cost nothing.

When a turn ends

The Game keeps a set, waitingOn, of the Seats people are still planning. StartTurn fills it. Computer Seats are never in it, because StartTurn makes their Orders itself.

  1. StopSeat removes one Seat, in a write that requires the same turn, the Seat still in the set, and the revision it names. A retry changes nothing.
  2. DynamoDB applies those writes one after another, so the set empties exactly once.
  3. The stream shows the change to the Turn Lambda, which resolves if the set is empty. The stream retries, so a crash cannot strand a turn.
  4. StartTurn commits only if the Game is still on the previous turn.
  5. At the deadline Scheduler wakes the Turn Lambda, which empties the set and marks those Seats as timed out. Each Seat's last saved Orders stand.
  6. CreateOrders checks its Seat is still in the set and the Game is not STOPPED.

No turn can loop on its own

AWS stops some runaway Lambda loops, but its documentation says it cannot detect one that runs through DynamoDB. So three rules of ours bound it: a Game has a turn limit, a Game with no people never uses the stream, and a Game where nobody acted for three turns in a row stops itself.

How this differs from your budgeter

Your budgeter is simple because the browser is the backend: it reads a budget, changes it, and writes the whole document back with setDoc. That is right when the writer owns the data. Here a browser must not see another player's orders, roll dice, or decide that an order is legal. So every write still goes through a function, and each action costs the same code as on AWS.

What stays simple is real: the sign-in pop-up, tokens attached for you, and onSnapshot for push with reconnection done by the SDK. That replaces Cognito, the WebSocket API, the connect check and the connection list.

Which one

Decided on 24 November 2026: AWS only. The Firebase design stays here as the alternative that was weighed.

I recommend AWS with API Gateway. Firebase is simpler to build and nicer for push. It loses on the one thing you named as the worst case: its database cannot be capped, and refused traffic is not clearly free. On AWS, refused and throttled traffic is documented as free, and the rate limit bounds the rest.

The choice is reversible. The game service knows nothing about either, so changing later means a new storage adapter, a new remote client and a new sign-in, with the rules, actions and tests kept.

Contracts between components

Redux and GameClient Built

interface GameClient {
  send(command: ClientCommand): void
  subscribe(listener: (event: GameEvent) => void): () => void
}
type ClientCommand =
  | { kind: "create", scenarioId, assignments, timerMinutes, seed? }
  | { kind: "game", gameId, command: GameCommand }
  | { kind: "leave", gameId }
type GameEvent =
  | { kind: "view", view: PlayerView }
  | { kind: "refused", refusal: GameRefusal, turnNumber? }
  • Sending never returns a result. What happened arrives as an event, at once or seconds later.
  • A view whose version is lower than the one held is ignored, so late answers cannot undo newer ones.
  • A refusal for an earlier turn is not shown against the current one.
  • Lobbies need new commands here: joining and taking a seat happen before a game exists.

Remote client and the HTTP API Proposed

POST /CreateOrders
Authorization: Bearer <Cognito token>
{ gameId, factionId, turnNumber, revision, orders }
  • One route for each action. An unknown route, a missing token or a bad one never reaches our code.
  • The site's origin is the only one allowed by CORS.

WebSocket API and the remote client Proposed

server to browser: { gameId, version }
  • Nothing else is ever sent, and the browser sends only keep-alives.
  • A lost socket costs nothing: on reconnecting the client calls GetGame with the version it knows.
  • The token is checked as the socket opens. It is sent as a query value, because browsers cannot set socket headers, so it must not be logged.

HTTP API and the Game Lambda Proposed

{ action: "CreateOrders", player: { sub }, body: unknown }
  • sub comes from the verified claims and never from the body.
  • Someone with no Seat and no invite code gets "unknown game".

Game Lambda and the game service Built

  • Pure: the same inputs always give the same answer. Time is passed in.
  • A refused command changes nothing. A repeated or late one is harmless.
  • Records are plain JSON. A test plays five turns through JSON each turn and compares every byte.
  • The caller must serialize writes: the service does not know about other callers.

Game Lambda and DynamoDB Proposed

getGame(gameId)                               -> Game, Seats
createOrders(game, faction, turn, rev, orders) -> stored | seat-stopped | wrong-turn | older-revision
stopSeat(game, faction, turn, rev)             -> stopped | already-stopped | wrong-revision
stopGame(game) / startGame(game)               -> done | not-host | people-are-remote
startTurn(game, turn, record)                  -> started | already-started
  • Each is one conditional write or one transaction. The condition is the contract.

DynamoDB stream, Scheduler and the Turn Lambda Proposed

  • The stream sends the changed Game; the Lambda acts only if it is PLAYING, has a person, and waitingOn is empty or missing.
  • Scheduler sends { gameId, turnNumber }. Early, late and repeated calls are safe, because the Lambda checks its own clock and the turn number.
  • After any Game change it posts to that Game's sockets. A failed post removes that socket from the list.

Decisions

Settled

  • AWS only: API Gateway, Lambda, Cognito and DynamoDB. The design is parked; the questions below are still open.
  • Actions are VerbNoun with your eight verbs and four nouns.
  • Pause is StopGame, allowed only while one person holds every human Seat.
  • Games with only computers run to their end and are read with ListTurns.
  • Orders are refused at submission. The last saved Orders stand at the deadline.
  • The seed is hidden until the Game ends, and may be given at creation.
  • Local games use this same path.

For you to decide

  1. Absent players. A Game stops after three turns with nobody acting. Should a computer instead take over one absent player's Seat?
  2. Chosen seeds. Whoever chooses one can work out future dice. Any Game with a visible mark, or only Games with one person?
  3. Timer lengths. Add 30 and 60 minutes, or a day or more?
  4. Environments. Production only, or a test environment too?

To test before building

  • That a refused WebSocket $connect is free, as the general pricing wording says.
  • What a DynamoDB set looks like after its last member is removed.
  • Whether Cognito counts a refused first sign-in as an active user.
